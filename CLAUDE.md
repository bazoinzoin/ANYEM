# Anyem — notes pour Claude Code

RPG tour par tour roguelite, JavaScript vanilla en modules ES, sans build ni dépendance.
Lire `docs/PROJECT_STATUS.md` (état, feuille de route) et `docs/DESIGN_DOC.md` (vision, référence de design) avant toute évolution de gameplay.

## Commandes

- `npm start` — serveur local sur http://localhost:8000
- `npm test` — tests unitaires (`node --test`)
- `npm run build` — régénère `dist/anyem.html` (jeu en un seul fichier, jouable en double-clic). **À lancer et commiter après toute modification de `index.html`, `css/` ou `src/`** : un test vérifie qu'il est à jour. Le joueur utilise ce fichier, il n'a pas Node.
- Images : déposer les PNG dans `assets/` (crédits dans `assets/CREDITS.md`) ; `npm run build` les intègre en data URI dans `src/ui/assetData.js` (généré, un test vérifie qu'il est à jour) ; chargement via `image(clé)` (`ui/sprites.js`), clé = chemin sous `assets/` sans extension.
- Versions : la version officielle jouable est le jeu Windows (`desktop/`, Electron) publié sur GitHub (Releases) à chaque étiquette `vX.Y.Z` par `.github/workflows/release.yml`. Numéro dans `package.json` = `src/version.js` = `desktop/package.json` (`npm run desktop`), section dans `CHANGELOG.md` (un test le vérifie). Nouvelle version jouable : monter la version, écrire sa section du journal (en français, point de vue du joueur), voir `docs/RELEASES.md`. Bêta tant que la version est en 0.x (pré-version GitHub, « bêta » sur l'écran titre) ; 0.0.x = étapes d'avant le jeu Windows ; retirer une version : workflow « Retirer une version » (`delete-release.yml`).
- Logo : `python3 tools/logo.py` régénère `assets/logo/*.png` et `dist/anyem.ico` (icône Windows) ; l'icône de l'onglet (`<link rel="icon">` de `index.html`) est intégrée par `npm run build`.
- `tools/build.mjs` ne gère que `import { … } from '…'` et `export function|const|let|class` : s'en tenir à ces formes.

## Architecture : couches à respecter

`data/` → `game/` → `ui/` (une couche n'importe jamais une couche à sa droite).

- `src/data/` : données pures (classes, ennemis, donjons). Ajouter du contenu ici, pas dans la logique.
- `src/game/` : règles du jeu, **sans DOM ni timers**, testables sous Node. Tout aléatoire passe par `game/rng.js`.
- `src/ui/` : rendu par template strings, un fichier par écran dans `ui/screens/`, navigation via `ui/router.js` (`goTo`, `showHub`). Le jeu s'ouvre sur le menu principal (`ui/screens/title.js`, écran `title`, plein écran : clairière animée, titre orné, menu à droite ; Nouvelle partie et Charger via les emplacements de sauvegarde (`ui/screens/slots.js`, `openSlots`), Options, Quitter, Debug = partie de test `setupDebugGame` dans `game/debug.js`, réglages `DEBUG` de `config.js`).
  Sauvegardes : `game/save.js` (pur, testé : `makeSave` / `applySave`, graphe d'objets `encodeGraph` qui garde les liens partagés, donc sauvegarde possible en plein combat ; `SAVED_FIELDS` = champs de l'état enregistrés — un nouveau champ de partie doit y être ajouté et dans `freshGame` de `state.js`), stockage des 4 emplacements et options dans `ui/saves.js` (localStorage), écran `slots` (`openSlots('new' | 'load' | 'save')`). Une aventure = un emplacement (`state.saveSlot`). Menu Échap : `ui/pause.js` (Reprendre, Sauvegarder, Options, Quitter) ; pendant la pause les tours ennemis attendent : programmer les délais de combat avec `later` (`ui/pauseClock.js`), jamais `setTimeout` directement. Chargement d'un combat : `resumeCombat` (`ui/encounter.js`).
  `ui/encounter.js` rythme les combats (délais des tours ennemis) autour du moteur `game/combat.js`.
  Écran de combat plein écran sans défilement (`ui/screens/combat.js` : fenêtres équipe / commandes / infos, état d'interface `ui`) ; scène animée : `ui/battleStage.js` (canvas, équipe à gauche, monstres à droite, clic sur un personnage pour cibler) ; `encounter.js` photographie le combat avant chaque action (`snapshotBattle`) et passe le résultat à `playAction` ; ce qui a changé et le geste (bond / sort) sont calculés dans `ui/battleDiff.js` (pur, testé).
- Interface pixel art : `ui/skin.js` (images du pack d'interface et polices en variables CSS, `applySkin` au démarrage), `css/skin.css` (chargé en dernier), icônes via `iconHtml(n°)` et les choix de `ui/icons.js` (équipement : planche `icons/equipment.png`, une colonne par rareté, numéros ≥ `EQUIP_BASE` via `itemIcon`) (jamais d'emoji pour un objet, un effet ou une compétence). **Tous les écrans sont plein écran sans défilement** : cadre commun `frame` / `wireFrame` et grilles d'icônes paginées `itemGrid` / `wireGrid` / `fitGrids` (`ui/screenFrame.js`), portraits `portrait` / `drawPortraits` (`ui/portraits.js`) ; village et expédition = canvas plein écran (`fitCanvas`, `clampView` dans `ui/viewport.js`) + interface posée dessus (`ui/hud.js` : `partyHud` — encadrés de l'équipe repliés par défaut, affichés par le bouton Personnage, clic sur un héros = son menu Personnage, `wireHud` —, `hudButton`, `toast`, aide aux déplacements derrière `helpButton` « ? »). Une mise en page d'écran = classe `lay-…` dans `css/skin.css` ; vérifier à 1280×720 et 1024×640.
- Manette : `ui/gamepad.js` (API Gamepad, lancé dans `main.js`) imite clavier et souris : sur les cartes, croix / stick = flèches, A = Espace (ou l'échelle), Y = passer aux menus ; ailleurs, curseur `.pad-focus` de bouton en bouton (navigation spatiale pure `pickNext` dans `ui/gamepadNav.js`, testée), A = clic, B = retour (`#scrBack`, `#backHub`… sinon Échap), LB / RB = pages ou héros, Start = Échap. Tout élément cliquable doit être un `button` ou porter un des attributs de `FOCUSABLE` pour être atteignable.
- Héros personnalisés (création de personnage) : catalogue `data/appearance.js` (`HAIR_STYLES`, `HAIR_COLORS`, `EYES`, `SKINS`, `TOPS` = corps d'un héros du pack + couleurs remplacées ; tous les corps ont la même taille (cou à `cut` 24 : les corps courts du pack ont été allongés dans `assets/heroes/`), une nouvelle tenue ne doit pas changer la taille du héros, `BOTTOMS`, `CLASS_LOOKS`), règles `game/appearance.js` (`hero.look`, `sanitizeLook`, `cycleLook`, `lookOf`). Rendu : corps sans tête `assets/heroes/body_*.png` (14 images × 4 directions de 48 px : attente, marche, attaque, dégâts, sort), coupes dessinées en texte dans `ui/heroHeads.js` (face / profil / dos, grille de 16 colonnes, `HEAD_OFFSETS` = position de la tête par image), assemblage pur `composeHero` (`ui/heroCompose.js`, testé). Une nouvelle coupe = une entrée dans `HAIR_STYLES` + ses 3 vues dans `HEADS`.
- Bestiaire graphique : chaque ennemi de `data/enemies.js` a une entrée dans `ENEMY_LOOKS` (un test le vérifie) ; planches `assets/mobs/<Monstre>_<idle|walk|attack|hit|die>.png`, tailles dans `ui/mobSheets.js` (généré).
- Chiffres d'équilibrage globaux : `src/config.js`.
- Les stats d'un héros se lisent **toujours** via `getStats(hero)` et ses compétences via `getSkills(hero)` (`game/party.js`) : c'est là que l'équipement (et plus tard talents et buffs) s'applique. Ne pas lire `CLASSES[...].base` ou `.skills` directement ailleurs.
- Niveau max 50 (`XP.maxLevel`), 1 point de talent par niveau ; chaque orientation = 15 paliers : gros paliers 0 (sort de départ), 2 à 12 (compétence ou passif important, obligatoires) et 14 (signature, `SIGNATURE_TIER`) ; petits paliers 1 à 13 (impairs) = trois bonus de stats, deux se prennent (`CHOICE_PICKS`, `CHOICE_RANKS` rangs) ; 36 points l'orientation ; un palier s'ouvre quand les précédents sont complets (`tierOpen`, `chosenInTier`, `excludedInTier`) ; sauvegardes anciennes : `sanitizeTalents` (appelé par `applySave`). Un bonus ne doit pas précéder la compétence qu'il renforce (un test le vérifie). Tests : `learnPath` (`tests/helpers.js`). Équilibrage : `tests/balance.test.js` (dégâts par round de chaque orientation, ±20 % au niveau 50) — à relancer après toute retouche de compétence.
- Un héros commence sans sort : les sorts de départ (`starterSkills` de la classe) s'apprennent au palier 0 des orientations (nœuds `skills`, voir `nodeSkills`). Tests : `learnStarters` (`tests/helpers.js`).
- Talents : contenu dans `data/talents.js`, règles dans `game/talents.js` ; leurs effets passent par `getStats` (flat/pct/passive) et `getSkills` (skill/skillMod). Buffs/debuffs : **catalogue unique `data/effects.js`** ; une compétence les applique via `effects` / `selfEffects` (`[{ id, turns, power? }]`) et décide seule des cibles. Ne jamais définir un effet dans une compétence ; un nouvel effet s'ajoute au catalogue (un test le vérifie). Instances en combat : `makeStatus` (`game/statuses.js`).
- Zones : chaque donjon = 3 sous-zones de 5 étages (`subzones` : niveaux, `pool`, `elites`, `boss` ; `zone()` calcule floors/pool/bosses), niveaux 1 à 50 ; `subzoneOf`, `floorInSubzone`, `floorLevel` dans `game/dungeon.js`. Le butin prend le niveau des ennemis (`combat.level`), plafonné au niveau du joueur (héros le plus haut de l'équipe) : `lootLevel` (`game/progression.js`).
- Donjons : contenu dans `data/dungeons.js` / `data/enemies.js`, logique dans `game/dungeon.js` (expédition, étages, boss, points de passage) ; `ui/encounter.js` lance le combat de l'étage (`startFloor`) et applique l'issue (`winFloor` / `loseExpedition`). Capacités ennemies = `abilities` au format des compétences, cibles `hero` / `allHeroes` / `self` / `allAllies`.
- Consommables : données dans `data/consumables.js` (`use` : 'combat' / 'map', `target`, `effect`), logique dans `game/consumables.js` (`applyConsumable`, `useOnMap`). Tout nouvel effet négatif doit être ajouté à `DEBUFF_KEYS` et avoir un remède dédié (un test le vérifie).
- 6 classes (`CLASS_ORDER`), équipe de 4 au choix (`createParty(names, classes)`). Chasseur = Énergie sans combo, pièges (`trap`) ; Paladin = Force ou Intelligence selon l'orientation, soins `physHeal`, Intercession (`redirect`).
- Classes à Énergie (Voleur, Chasseur) : plusieurs actions par tour (`resource.multiAction`, `actionCosts`), points de combo (`comboGain` / `finisher`) : règles dans `game/combo.js` ; un finisher se lance via `atCombo(skill, points)` (puissance et effets par point ; `fullAt` : pleine puissance dès n points, Empoisonneur).
- Expédition sur carte : `game/floorMap.js` (génération seedée, brouillard, IA des monstres), `stepParty` / `takeLadder` / `winFight` / `canExplore` dans `game/dungeon.js`, rendu et contrôles dans `ui/mapView.js` ; 2-3 groupes de monstres par étage ; tests : `winNextFight` / `clearFloor` (`tests/helpers.js`) ; les debuffs restent entre les combats (filtrés dans `createCombat`) ; soins/purifications hors combat : `game/field.js`.
- Événements d'expédition : contenu `data/events.js` (choix, issues, coûts, `look` = apparence sur la carte : personnage `hero` ou objet `object`), règles `game/events.js` (`rollEventKey` à la génération de l'étage, `rollEvent(level, key)` en marchant dessus, `chooseEvent`, marchand ambulant) ; `expedition.event` bloque l'exploration. Dessin : `drawEventMarker` (`ui/mapView.js`).
- Difficulté : `DIFFICULTIES` (`config.js`, 6 niveaux de Balade à Insanie), règles dans `game/difficulty.js` (`enemyPower`, `lootRules`, `difficultyLevel` : niveau 50 partout à partir d'Horreur) ; la puissance passe à `createCombat` via `floorCombat`, le niveau via `expeditionLevel`, le butin via `rollLoot(…, { difficulty })`. Matéria toujours meilleures que l'équipement (boss compris), jamais de matéria divine. Médailles : `MEDALS.from` (config), règles `game/medals.js` (`awardMedal` dans `winFight` au dernier boss, `zoneMedals`, stockées dans `game.dungeons[zone].medals`), dessin pixel art `ui/medals.js` (`medalPixels` pur : métal et ornements selon le rang relatif, la dernière plus grande ; une nouvelle zone = une entrée dans `ZONES`), affichées aux portails. Défaite : `applyDefeat` (or, sac jamais vidé, équipement porté à partir de Guerre) → écran `defeat`.
- Village à parcourir : carte et habitants dans `data/village.js` (une maison par habitant avec `door` et panneau `signs`, habitant `home` ; intérieurs dans `data/interiors.js` (façon RPG Maker : plafond + façade de 2 cases `interiors_A4`, sol A5, mobilier `FURNITURE` = rectangles de tuiles entières des planches `interiors_B` / `interiors_C` / `cozy_B`, jamais une découpe au pixel ; un test vérifie emprises, chevauchements et accès) ; scènes `sceneOf(lieu, résidents)` et `villageStep(pos, dx, dy, scène)` → `enter` / `leave` dans `game/village.js`, `state.village.place` / `residents` tirés par `rollResidents` à chaque arrivée ; un habitant = un service ; maisons = images entières de `buildings_obj` avec portes, fenêtres, enseignes et cheminées posées dessus (`decor`) ; objets et arbres en rectangles pixel `[planche, x, y, l, h]`), marche dans `game/village.js`, rendu `ui/villageView.js` ; `hub.js` associe chaque service à son écran (`openService`) ; portails : `ui/screens/portals.js`. Personnages (cartes, combat, portraits) : `drawActor` (`ui/actors.js`, animations `anim` / `animT`, image choisie par `packFrame`), tous issus des packs Franuka : héros via `heroSprite(hero)` / `lookSprite(look)` (`ui/heroSprite.js`), monstres via `enemySprite(clé)` (`ui/mobSprites.js` : `ENEMY_LOOKS` = planche + recoloration `tint`, taille `mobScale` : normal ×1, élite ×1,5, boss ×2, boss plafonnés à `BOSS_BODY` px en combat avec aura ; boss d'Akari21 = planches `Minotaur`, `FlyingDemon*`, `Gorgon`, `Wendigo`, `SnowWendigo` avec anim `cast`), habitants dans `NPC_SPRITES` (`ui/spriteCatalog.js`, villageois `assets/townsfolk/`). L'équipe marche en file indienne derrière le premier héros ; un pas = 155 ms (`STEP_MS`), touche maintenue gérée par `holdToWalk` (`ui/heldKeys.js`, ignore la répétition du clavier), images de marche par pas (`stride` / `progress` de `drawActor`).
- Décors : packs Raven Fantasy achetés par le joueur (archives dans `texture zip/map/`, à ranger par type : map, personnages, effets…), préparés dans `assets/raven/` : planches RPG Maker MV réduites en tuiles de 16 px (`<pack>_A1/A2/A4/A5`, autotiles `mvFloorQuarter` / `mvWallQuarter` dans `ui/autotile.js`) et planches d'objets (`<pack>_obj`, objets repérés en pixels). Étages : un thème par sous-zone dans `ui/mapThemes.js` (`themeOf(donjon, étage)` : fond, sol des salles / couloirs, murs A4 avec face de 2 cases ou liquide A1, objets posés par règles `props`). Fonds de combat : `ui/battleBacks.js` (`backdropOf`, `battleBack`), composés à partir du thème de la sous-zone (mur, lac ou lisière d'arbres au fond, sol, petits objets) et précisés par `BACKS[donjon][sous-zone]` ; dessinés par `battleStage.js`.
- Village : auberge (`game/roster.js` : recrutement niveau 1, réserve `state.reserve` sans XP, max `INN.maxReserve`, échanges, renvoi `dismiss`), bestiaire (`game/bestiary.js`, stats sans hasard via `enemyStats`) et banque (`game/bank.js` : or, objets, consommables, matéria à l'abri des défaites). Matéria et consommables sont dans le sac du joueur (`state.materia`, `state.consumables`).
- Positions corps à corps / distance, riposte, portée des armes : `game/position.js` (`hero.position` = stratégie, `unit.row` = position en combat). Vitesse d'attaque des armes : `WEAPON_TYPES[].speed`, appliquée dans `getStats`.
- En combat, lire les stats via `statsOf(unit)` (`game/units.js`) : il ajoute les buffs/debuffs et Berserk à `getStats`.
- Équiper/retirer passe par `game/equipment.js` (`equip`, `unequip`, `slotsFor`) : règles de maîtrise, deux mains, retour au sac.
- Légendaires (`LEGENDARIES`, `data/items.js`) : 3 par orientation, chacun renforce un gros palier (`power.skillMod`, ou stats + `requires` = nœud renforcé) ; communs sans `classKey` (passifs de combat `freeMove`, `echoChance`, `dmgDealtPct` / `hpCostPct`, `startEffects`). Pouvoirs lus via `legendaryPowers(hero)` (`game/party.js`) dans `getStats` et `getSkills`. Un test vérifie qu'un légendaire vise bien un gros palier de son orientation.
- Rareté Divin (boss seulement, à partir de Guerre) : pas de matéria divine (`MATERIA_RARITIES`) ; pouvoir légendaire absorbé = `item.absorbed`, l'objet prend aussi le nom du légendaire (Forge divine, `absorbLegendary`).
- Forge (`game/forge.js`) : matéria par catégorie (`materiaKind` : arme / armure (+ bouclier) / bijou), décraft, amélioration, fabrication (`craft`, `craftProblem`). Runomancien : `game/runes.js` (`rerollSecondary`).
- Stats d'un objet : toujours via `itemStats(item)` (`game/items.js`), qui applique l'amélioration +1..+5 ; `item.stats` = stats de base. Nom affiché : `itemName(item)` (`ui/items.js`).
- Dégâts : `rollHit` / `estimateHit` (`game/formulas.js`) — mêmes calculs pour le jet et l'estimation affichée. Physique = `physPower` (Attaque des armes + Force/Agilité selon `physStat` de la classe) ; magique (`skill.magic`) et soins = `magPower` (Intelligence). L'Intelligence ne doit jamais renforcer une attaque à l'arme.
- Objets communs : exactement stat(s) obligatoire(s) + stat principale (armure : Armure, qui compte comme Défense et Défense magique dans `getStats` ; bouclier : Armure + Blocage ; bijou : aucune stat obligatoire, stat principale renforcée) ; secondaires (`item.bonus`) à partir de peu commun ; la secondaire Mana (`mana`) ne sert qu'aux classes à Mana (`usesMana`, comptée dans `resMax` ; détail `resMaxBase` / `resMaxTalents` / `resMaxItems` au survol de la ligne Mana, jamais listée parmi les stats). Armes, armures et bijoux peuvent sortir en Force, Agilité ou Intelligence. Affichage des lignes de stats : `itemStatLines(item)`.

## Conventions

- Textes du jeu et commentaires en français ; identifiants en anglais.
- Tout texte dynamique inséré dans du HTML passe par `esc()` (`ui/html.js`).
- Lexique : les mots de `data/glossary.js` (plus les effets de `data/effects.js`) sont soulignés automatiquement dans tous les textes affichés, avec une bulle au survol (`ui/glossary.js`, observateur lancé dans `main.js`) ; un nouveau terme du jeu s'ajoute à `data/glossary.js` (`cs: true` pour un mot courant qui ne compte qu'avec sa majuscule). Pas de soulignement dans les boutons, titres, ni un texte qui a déjà une infobulle (`.no-gloss` pour exclure une zone).
- Toute nouvelle règle dans `src/game/` s'accompagne d'un test dans `tests/`.

## Préférences du joueur (à respecter)

- Toujours demander la cible explicitement, même s'il n'y en a qu'une.
- Afficher les dégâts/soins estimés avant de valider une action (mêmes fourchettes que le jet réel, via `game/formulas.js`).
- Tours ennemis jamais instantanés : délai + mise en évidence de l'unité active.
- Accès facile aux statistiques des personnages.
- Ambiance JRPG pixel art avec de vrais sprites à terme.
